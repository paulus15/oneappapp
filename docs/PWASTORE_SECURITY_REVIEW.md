## 3. Priorité faible et informations

- Brute-force du code de réinitialisation très lent mais cumulable (~0,06 %/jour) → verrou cumulatif par compte.
- Énumération des comptes à l’inscription ; verrouillage d’un compte déclenchable par un tiers.
- Tableaux libres sans taille max (`payload`, `languages`, `compatibility`) ; déduplication analytics contournable.
- Nom civil du développeur public même avec un nom public choisi ; motif de modération d’un avis rétabli visible.
- Empreinte des PWA par lien limitée au HTML : un `app.js` modifié après approbation n’est pas détecté (à annoncer comme limite).
- Copie des ZIP basée sur les tailles déclarées (atténué : dépôt ZIP désactivé).
- Sous-domaines d’hébergement partageant un même site : inscrire le domaine à la Public Suffix List.
- Liens issus de données anciennes non filtrés côté front (le serveur exige HTTPS) ; couleurs injectées sans filtre à deux endroits ; composant de modèle Quasar avec `target="_blank"` sans `rel`.
- Historique de recherche conservé après déconnexion ; un `console.log` restant.
- Build de production possible sans `VITE_API_URL` (repli silencieux vers l’adresse locale).
- Accessibilité : dialogues sans nom accessible, code pays non annoncé, « Copié » non annoncé, grille du dossier admin étroite à 390 px.
- Requêtes N+1 (file admin, collections), index manquant sur `status, is_active`.
- `CORS *` par défaut, `APP_DEBUG` à vérifier en production, absence de `frame-ancestors` en en-tête HTTP côté front.
- Changer `APP_KEY` invalide toutes les empreintes (vues, appareils, codes) : utiliser une clé dédiée.

## 4. Ce qui est solide (vérifié)

- **Séparation des rôles** : seuls les modérateurs décident, jamais sur leur propre app ; l’admin ne peut ni modifier une fiche, ni déposer, ni soumettre, ni publier à la place du développeur.
- **Ce qui est approuvé est ce qui a été soumis** : empreinte de la fiche, hash du ZIP au moment de l’approbation et du déploiement ; verrous de base de données contre les doubles décisions et doubles soumissions.
- **Pas d’IDOR** : documents d’identité, avis, signalements, notifications, statistiques, ressources externes vérifient la propriété.
- **SSRF** : HTTPS uniquement, adresses privées refusées, IP épinglée contre le DNS rebinding, redirections revalidées, taille limitée.
- **Uploads de couverture** : contenu réel vérifié, bombes de décompression évitées, recodage sans métadonnées, un dossier par envoi.
- **Hébergement isolé** : origine séparée, lecture seule, protection contre la traversée de chemins, types MIME en liste blanche.
- **Authentification** : codes à usage unique hachés et limités, double authentification à la connexion, jetons qui expirent et sont révoqués aux changements sensibles.
- **Front** : aucun `v-html` ni injection HTML, liens externes filtrés sur la fiche, pas de redirection ouverte après connexion, CSP sans `unsafe-eval`, lancement d’application sécurisé (`opener` coupé, HTTPS exigé).
- **Traductions du front** : 666 clés en français et en anglais, aucune manquante ; 1 059 appels de la couche `ui()` couverts.
- **Aucun secret versionné** dans les dépôts.
